# 1.7.5 — Native Bisect Ownership

Status: Implemented; automated verification passed.
Approved: 2026-10-17, “Pode tratar o achado 1”.
Scope: B1 from the [bisect review](../bug-bisect-fragility-review-2026-10-17.md).

## Define

A terminal can reset and restart bisect with exactly the extension's endpoints
and answer history. The resulting log can be identical. The old ownership check
then accepts and can reset that replacement when the user stops the old search.

Require a persisted identity of the native instance in addition to the expected
HEAD and command log. Verify it before answers, undo, checkout and reset, and
before capturing command results as owned. Preserve original return destinations,
worktree isolation, legitimate reload/rebuild and interrupted checkout/restore.
Keep B2 (durable-transition reconciliation) and B3 (typed entry target) separate.

Acceptance: an external replacement, including identical start contents and log,
must retain its native metadata and checkout after blocked controls. Legacy saved
sessions must not silently acquire an active instance's identity. No new Git refs,
automatic reset/cleanup, dependency, protocol or package-version change.

## Build

- `BisectGit.nativeIdentity` locates worktree-local `BISECT_START` using Git's own
  `rev-parse --git-path`; it does not assume a `.git` directory layout.
- `nativeIdentity.ts` reads at most 16 KiB from a regular start file and hashes its
  contents with device/inode, birth/change/modify nanoseconds and size. It checks
  the descriptor before/after reading and the path's final identity. Read access
  time is excluded. No ownership marker is written to the repository.
- The probe observed immediate inode reuse after native reset, even with the same
  file contents. Creation/change/modify metadata therefore participate too. The
  identity stays stable across ordinary answers, checkout and reads; a native
  restart changes it. Undo clears the old identity only after its owned reset and
  captures the new instance it starts.
- The opaque identity is validated and persisted only in the host session. It is
  stripped from webview state. The existing log-extension checks remain required.
- Stored sessions lacking an identity remain available for recovery context, but
  cannot adopt an active native bisect. The error explains Detach Controls/manual
  recovery; that confirmed action releases only extension ownership.
- HEAD validation and native-instance validation are separate methods to preserve
  the existing complexity limit. No quality threshold or baseline is relaxed.

Context7 `/git/htmldocs` confirmed no-checkout selection through `BISECT_HEAD`
and worktree-aware path resolution; it did not supply a native session-id API.
See [Git bisect](https://git-scm.com/docs/git-bisect) and
[Git worktree details](https://git-scm.com/docs/git-worktree#_details).
File-instance behavior is established by local Git fixtures, not inferred from
those documentation excerpts.

## Deliver and limits

Only disposable repositories are mutated during verification. OS metadata is an
observed instance fingerprint, not an authentication secret or a cross-process
Git lock. The extension does not serialize arbitrary terminal Git commands;
checks reject observed changes at operation boundaries. Manipulating/restoring
all filesystem metadata is outside this guarantee. Legacy active sessions can
require manual restoration, rather than an unsafe automatic identity upgrade.

The maintainer authorized committing the changes on 2026-10-17. No version bump,
VSIX or publication is part of this handoff. Rollback
must keep identity reads, persistence, validation and ownership callers aligned.
