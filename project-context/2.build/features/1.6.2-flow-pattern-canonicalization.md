# Flow Governance: Canonical Pattern Case

Status: Implemented; automated verification passed; manual Windows validation pending
Target version: `1.6.2`

## Goal

Keep Flow Governance branch recognition case-flexible while making governed branch creation
deterministic and portable across case-sensitive and case-insensitive filesystems.

## User Workflow

1. A repository defines a start-anchored Flow pattern such as
   `^Latam/[fF]eature/.+$`.
2. Flow Governance classifies both `Latam/feature/...` and `Latam/Feature/...` as features.
3. A governed start action accepts a suffix or either complete spelling and creates the canonical
   `Latam/feature/...` spelling because `f` is the first member of `[fF]`.
4. Creation stops before mutation if an existing local or remote-tracking branch differs from the
   generated name only by letter case.

## Scope

- Interpret `[xX]` and `[Xx]` in deterministic, start-anchored pattern prefixes for all seven
  configured pattern kinds.
- Preserve full-regex classification behavior.
- Canonicalize release, feature, task, bug, and hotfix governed creation.
- Derive equalization names from the configured release/feature and sync prefixes.
- Use the configured sync naming rule for legacy Pull Request target inference.
- Detect exact and case-only local or remote-tracking ref collisions before governed creation.
- Keep package patterns ready for canonical-prefix analysis even though package creation has no
  current user workflow.

## Non-goals

- Generate arbitrary strings from regular expressions.
- Infer canonical output from ranges, negated classes, multi-letter alternatives, groups, or
  quantified expressions.
- Change the Flow configuration schema or default patterns.
- Rename existing refs or change Git's global or repository case settings.

## Touched Surfaces

- Pattern analysis and governed branch-name resolution.
- Equalization naming, creation, and Pull Request target inference.
- Flow Governance workflow configuration routing.
- Flow Governance tests, product documentation, architecture notes, and release readiness.

## Acceptance Criteria

- `[fF]` recognizes both cases and emits `f`; `[Ff]` recognizes both cases and emits `F`.
- The rule works for release, sync, package, feature, task, bug, and hotfix patterns.
- Full alternate-case names and suffix-only inputs resolve to the same canonical created name.
- Unsupported regex constructs retain recognition semantics without guessed canonical output.
- Configured equalization creation and legacy sync-target inference use the same canonical rule.
- Exact and case-only collisions stop before branch creation.
- Existing default Flow Governance behavior remains unchanged.

## Risks And Controls

- Pair order becomes observable during creation; README guidance calls out the new semantic.
- Filesystem case folding varies beyond ASCII; canonical pair interpretation is deliberately
  limited to ASCII letters and collision comparison is normalized before case folding.
- Repository-controlled regex remains behind the existing bounded compilation and safety checks.
- Collision checks include loaded local and remote-tracking refs and retain the Git API lookup
  fallback used for exact local names.

## Manual Validation

- On Windows, configure `^Latam/[fF]eature/.+$`, start a feature from `main` or `release`, and
  confirm the created ref is `Latam/feature/...`.
- Repeat with `[Ff]` and confirm `Latam/Feature/...`.
- Create the opposite-case spelling first and confirm Flow Governance blocks the new branch before
  mutation with a case-conflict message.
- Prepare equalization with configured Latam release/feature/sync patterns and confirm the sync
  branch uses the configured canonical spelling.

## Release-note Impact

Flow Governance patterns can recognize either letter case while their ordered case-pair classes
define the canonical spelling used for governed branch creation and equalization.
