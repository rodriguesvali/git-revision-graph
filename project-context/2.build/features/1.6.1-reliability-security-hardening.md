# 1.6.1 Reliability and Security Hardening

Status: Automated implementation complete; final manual and release gates pending
Target version: `1.6.1`
Opened: 2026-07-28

## Goal

Correct the highest-value fragilities identified after the `1.6.0` release so repository-controlled
input, asynchronous refreshes, large worktrees and histories, and timed-out Git commands fail safely
without misleading or freezing the user.

## User Workflow

1. The user opens a repository, Revision Graph, Compare Results, or Show Log as usual.
2. Repository-controlled configuration and large Git data sets stay within explicit resource bounds.
3. Newer user actions retain ownership of the visible result when older asynchronous work completes.
4. Limits, failures, and timeouts are reported truthfully and leave the extension responsive.

## Scope

### Priority 0

- Bound Flow Governance config file size, JSON structure, string and collection sizes, and accepted
  regex complexity before runtime classification in `src/revisionGraph/flow/`.
- Prevent stale Compare Results preparation or refresh work from replacing a newer comparison,
  including when the active repository changes.

### Priority 1

- Revalidate repository config path identity at the final persistence boundary and reject symlink or
  path-substitution races without writing outside the intended repository file.
- Replace one-process-per-untracked-file unified-diff behavior with bounded aggregate work while
  preserving path safety, deterministic output, cancellation, and useful errors.
- Surface the Show Log filter scan ceiling and provide an honest continuation or truncation state
  instead of silently treating the first 2,000 commits as the complete history.

### Priority 2

- Escalate Unix Git process-group termination after a bounded grace period when `SIGTERM` does not
  stop a timed-out command.

## Acceptance Criteria

- Repository configuration exceeding documented bounds is rejected with an actionable diagnostic
  before unbounded parsing, allocation, or regex execution.
- Flow regex validation and runtime matching cannot monopolize the extension host with known
  pathological input; safe existing configurations retain their behavior.
- A config write cannot follow a symlink or replacement path outside the intended repository target,
  including a substitution occurring between validation and persistence.
- Only the latest Compare Results request for the owning repository may update its panel.
- Unified-diff generation uses bounded process and output resources for large untracked-file sets and
  preserves unusual-path handling.
- Show Log communicates when search was truncated and does not claim that an older matching commit is
  absent from unscanned history.
- Timed-out Git processes and their process groups are terminated after a bounded grace period on
  supported platforms, without signaling unrelated processes.
- Existing multi-repository, cancellation, error-modal, Git safety, and webview protocol contracts
  continue to pass.

## Risks

- Overly strict Flow configuration limits could reject legitimate repositories; limits need fixtures
  near both sides of each boundary and a clear diagnostic.
- Regex hardening can change accepted syntax; retain a deliberately documented compatibility subset
  and avoid silent pattern reinterpretation.
- Filesystem race mitigation differs by platform and filesystem; verify Windows and Unix behavior
  through the existing platform harness where direct atomic guarantees differ.
- Compare Results sequencing mistakes can suppress a valid update or dispose the wrong panel.
- Diff batching can change ordering, binary-file presentation, or unusual-path handling.
- Process escalation can target the wrong PID if identity and lifecycle checks are not preserved.

## Item 1 Decisions

- Repository config files are read through an open descriptor into a buffer capped at 64 KiB plus
  one sentinel byte, so size rejection does not require an unbounded read.
- JSON nesting is scanned outside string literals and rejected beyond depth 32 before `JSON.parse`.
- Repository config accepts at most 64 top-level fields, 32 `mainBranches` entries, 256 characters
  per main branch or regex, and 1,024 characters for the repository-relative config path.
- Regex safety uses a dependency-free tokenizer with a bounded 64-entry compilation cache. It rejects
  backreferences, more than 16 quantifiers, repeat counts above 1,000, adjacent potentially
  overlapping repetitions, and groups repeated more than once when they contain alternation or
  another quantifier.
- The shared compiler is used during normalization, branch classification, and governed branch-name
  validation so an internal caller cannot bypass the safety policy with a manually constructed
  normalized config.
- Default patterns, optional groups such as `^package(?:/.+)?$`, unquantified alternatives, and
  literal-separated repetitions remain compatible. Unsafe config fails closed and leaves normal
  graph loading available.

## Item 2 Decisions

- The target inspection now records exact bigint device/inode identity and hard-link count. The
  update opens without truncation and rejects a handle whose identity differs from the inspected
  file.
- The update reads, truncates, and writes through the same `FileHandle`; it does not return to
  pathname-based `writeFile` after validation.
- Unix opens add `O_NOFOLLOW`; Windows retains descriptor identity comparison because the flag is not
  supported there. Path and identity are revalidated after opening, immediately before persistence,
  and after persistence so a moved target is reported instead of silently claiming success.
- Writable configs with more than one hard link are rejected because modifying the shared inode
  could mutate a file outside the repository even when the repository pathname itself is regular.
- The Node filesystem contract was checked with Context7 `/nodejs/node/v22.17.0` and the local
  `@types/node` `20.19.43` declarations. `FileHandle.stat({ bigint: true })`, positional reads,
  descriptor truncation/write, and `O_NOFOLLOW` are compatible with the pinned project baseline.
- No runtime dependency, command, setting, contribution point, version, or Marketplace state
  changed.

## Item 3 Decisions

- Compare Results owns a monotonic request lease bound to the initiating repository path. Starting a
  newer request invalidates every older lease, including requests from another repository.
- Revision Graph/ref actions and Show Log acquire the lease before starting Git diff work. Show Log
  now publishes its loading state immediately so existing worktree refresh and unified-diff
  state-identity guards can observe that a newer comparison owns the panel.
- Only the current lease may publish a result, hide its loading state, or show empty-result and error
  messages. Stale Git work is allowed to finish, but its visible effects are suppressed.
- Completed-state deliveries without a lease claim fresh ownership. This preserves existing direct
  internal presenter calls while asynchronous producers use the explicit lease.
- Repository close, provider disposal, panel disposal, and graph-driven Compare Results hiding
  invalidate ownership. A late request therefore cannot recreate or repopulate a closed panel.
- Existing worktree refresh and unified-diff preparation retain their completed-state object identity
  checks. No cancellation API, runtime dependency, webview message, command, setting, contribution
  point, package version, or Marketplace state changed.

## Item 4 Decisions

- Worktree unified diff no longer starts one `git diff --no-index` process per untracked file. It
  writes a NUL-delimited, literal pathspec into a private temporary directory, points Git at an
  alternate index through request-scoped `GIT_INDEX_FILE`, records the paths with
  `git add --intent-to-add`, and emits all untracked patches with one `git diff`.
- The repository's real index is never read or modified by the untracked preparation. The temporary
  index and pathspec are removed after success, Git failure, output-limit failure, timeout, or
  cancellation.
- Untracked input is capped at 4,096 normalized unique paths and 2 MiB of UTF-8 pathspec data.
  Preparation output is capped at 256 KiB, each Git command retains the 15-second document timeout,
  and tracked plus untracked patch text shares the existing 32 MiB final output budget.
- `--literal-pathspecs` plus a NUL-delimited pathspec preserves spaces, Unicode, leading dashes,
  newlines, and option-like names without shell expansion. The final diff disables external diff and
  text-conversion drivers so repository configuration cannot reintroduce one process per path.
- Official Git documentation retrieved through Context7 `/git/htmldocs` confirms
  `GIT_INDEX_FILE`, `git add --intent-to-add`, and literal NUL pathspec behavior. Git 2.24 source
  documentation lacks `git add --pathspec-from-file`, while Git 2.25 includes it.
- To avoid introducing Git 2.25 as an undeclared minimum, exit code 129 from aggregate preparation
  activates a compatibility fallback. It uses literal argv batches capped at 128 paths and 16 KiB
  each, then retains the single temporary-index diff and every global bound.
- No runtime dependency, public API, command, setting, contribution point, package version, VSIX, or
  Marketplace state changed.

## Item 5 Decisions

- Filtered Show Log loading retains the existing 200-commit batches and 2,000-commit scan ceiling.
  The final batch requests one additional sentinel commit, which distinguishes a complete history
  of exactly 2,000 commits from an older unsearched history without adding another Git process.
- The sentinel is never filtered, displayed, counted, or included in paging. It only sets the
  `searchTruncated` result metadata when an older commit exists beyond the bounded search scope.
- A truncated empty search now says that no match was found in the first 2,000 commits and that
  older history was not searched. Truncated searches with matches show a visible status card with
  the same partial-scope warning.
- Existing `hasMore` semantics remain limited to additional matching entries. If incremental paging
  first discovers truncation, the presenter sends a full state so the status card appears without
  weakening the existing source-token and request-ownership checks.
- The shared scan-limit constant owns both backend enforcement and user-facing copy. No setting,
  command, contribution point, dependency, package version, VSIX, or Marketplace state changed.

## Item 6 Decisions

- Non-Windows Git children retain the existing `detached: true` spawn contract. The termination
  boundary snapshots the spawned `ChildProcess`, PID, and equal process-group ID before signaling;
  it never discovers a new PID or group during delayed cleanup.
- Unix termination sends `SIGTERM` to the original process group, waits 250 ms, and sends `SIGKILL`
  to that same group only if the original leader still has neither an exit code nor a signal code.
  An observed leader exit cancels the escalation, avoiding a delayed signal to a potentially reused
  process-group ID.
- Failed group signaling does not fall back to a later direct-PID lookup. Timeout, cancellation, and
  captured-output limits all reuse this termination path and reject only after graceful exit or the
  bounded escalation attempt. Windows retains the existing `taskkill /T /F` behavior.
- The Unix escalation regression uses delayed leader and descendant survival markers instead of
  `process.kill(-pgid, 0)` polling. GitHub-hosted macOS runners may reject that permission-sensitive
  process-group probe with `EPERM`; marker absence still proves both processes stopped, while a
  surviving process writes its marker and fails the test instead of being mistaken for an exit.
- The verification workflow already runs the full suite and platform harness on `macos-latest`
  alongside Ubuntu and Windows, so no matrix expansion or production fallback was required.
- Context7 `/nodejs/node/v22.17.0` and the local `@types/node` `20.19.43` declarations confirm that
  Unix detached spawn creates a new session/process-group leader, negative PIDs pass through
  `process.kill` to POSIX group signaling, and `ChildProcess.exitCode`/`signalCode` expose whether
  the original leader is still active.
- No dependency, public API, setting, command, contribution point, package version, VSIX, or
  Marketplace state changed.
