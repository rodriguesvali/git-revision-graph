# 1.6.1 Branch AI Descriptions

Status: Published in `1.6.1` by maintainer confirmation on 2026-07-29

## Goal

Make the existing description AI action usable when starting every governed branch kind, including
Feature, Task, Bug, and Hot Fix, while preserving explicit invocation, cancellation, prompt safety,
and Flow Governance source rules.

## User workflow

1. Open `Start New Release`, `Start New Feature`, `Start New Task`, `Start New Bug`, or
   `Start New Hot Fix`.
2. Enter the required name or ID/short-name combination and description.
3. Select the enabled sparkle action to improve the description.
4. Optionally select the stop action to cancel the exact pending request.
5. Review or edit the result before creating the branch through the unchanged governed workflow.

## Scope and decisions

- Extend the branch-form AI surface to `release`, `feature`, `task`, `bug`, and `hotfix`.
- Enable the action only after the complete branch name and description are present.
- Use the Release/Feature `Name` field directly and build the effective Task, Bug, or Hot Fix name
  from the ID and short-name fields before sending it; Task requires a numeric Dev Task.
- Carry the trusted branch kind through the bounded webview protocol and authorize the request with
  the same `isAllowedFlowStartSourceKind` policy used by branch creation.
- Select focused creation-description prompts for Release, Feature, Task, Bug, and Hot Fix without
  loading a diff or inventing facts not present in the form.
- Preserve request-ID cancellation, repository ownership, stale-result rejection, field limits, and
  explicit user initiation.
- Keep author styling from overriding the HTML `hidden` state if a future unsupported form is added.

## Non-goals

- No AI action for equalization forms.
- No automatic generation, branch mutation by the model, context-diff loading for branch creation,
  provider change, dependency, setting, command, contribution point, package version, VSIX, or
  Marketplace change.

## Acceptance criteria

- Release and Feature are enabled only when name and description are non-empty; Task, Bug, and Hot
  Fix are enabled only when their valid ID, short name, and description are non-empty.
- Release behavior remains available and uses its release-specific prompt.
- Every branch form displays the action.
- Release, Feature, Task, Bug, and Hot Fix requests carry their exact branch kind and effective name
  through validation, authorization, dispatch, prompt construction, result routing, and
  cancellation.
- Editing any participating field or closing/changing the form cancels ownership of the prior
  request; a late result cannot update another form.
- Prompts treat every form value as untrusted data and forbid invented causes, tests, incidents,
  risks, or release claims.
- Deterministic tests cover prompt specialization, protocol bounds, authorization, webview request
  construction, supported-kind/name rules, hidden styling, and cancellation surface identity.

## Architecture

- `src/revisionGraph/webview/runtime/flowBranchForm.ts` owns visibility, required-field readiness,
  effective branch-name composition, request identity, and matching result application.
- `src/revisionGraph/webview/runtime/flowAiTextInteractions.ts` and the shared protocol emit the
  generic `improve-flow-branch-text` intent with a bounded
  `release | feature | task | bug | hotfix` kind.
- Validation rejects unsupported kinds; authorization reuses governed branch-start source policy.
- `src/revisionGraph/flow/aiPrompts/shared.ts` dispatches focused branch-description instructions
  from the host-received, validated surface.
- The existing host workflow continues to own repository-scoped cancellation and stale-result
  rejection.
