# 1.7.0 Operation Processing Feedback

Status: Published; automated verification complete, manual smoke evidence not recorded
Last updated: 2026-09-04

## Goal

Give users immediate, truthful processing feedback while confirmed Git mutations are running, with
the label owned by the shared action workflow so Revision Graph and Show Log remain consistent.

## User Workflow

After the user completes any required prompt or confirmation, the active surface shows a specific
processing label until the Git operation resolves. Feedback is always cleared on success or failure.

## Scope

- Subtle feedback for publish, pull, push, and remote-branch deletion.
- Blocking feedback for sync, checkout, branch creation/overwrite, merge/abort, reset, stash
  save/apply/pop, and cherry-pick/start/continue/abort.
- Host-owned timing after the final user confirmation, shared by Revision Graph and Show Log.
- Latest-owner coordination in Revision Graph so stale operation completion cannot clear newer
  action, repository, render, status, or error state.
- Consolidation of preexisting Remote Tag, repository Fetch, Flow Governance remote-fetch, and
  equalization feedback onto the same `RefActionProgress` lifecycle.

## Non-goals

- No processing indicator for fast local-only deletion of branches or tags, stash drop, or local tag
  creation/deletion.
- No changes to Git semantics, confirmations, refresh policy, dependencies, or contribution points.
- Webview-owned progress remains for local projection, focus, reload, and view-transition work.

## Touched Surfaces

- Shared ref-action services and Git mutation workflows.
- Revision Graph loading overlay and subtle progress surface.
- Show Log loading chip.
- Generated-webview and ref-action regression tests.

## Acceptance Criteria

- Every scoped action starts feedback only when Git work begins.
- Revision Graph clears feedback only when the completing operation still owns the visible loading
  state; render and repository transitions invalidate obsolete ownership.
- Host-side Git processing uses one progress contract; legacy Remote Tag `start/stop` and dedicated
  Fetch/Flow loading-host contracts are removed.
- The indicator contains an operation-specific label and uses the reviewed blocking/subtle mode.
- Feedback clears in a `finally` path when the operation succeeds or fails.
- Excluded fast local actions remain free of unnecessary processing UI.

## Risks

- A stale Show Log request could clear newer state; source-token and repository ownership checks
  prevent it from updating a replaced view.
- A stale Revision Graph action could clear a newer action or render; latest-owner tokens and
  explicit invalidation on render, repository, status, and error transitions prevent that takeover.
- Starting feedback in the browser would cover native prompts; toolbar and context-menu mutations now
  delegate timing to the host workflow.
- Equalization preflight may require native confirmations. Remote checks and any confirmed source
  publication own short scoped feedback, while `Preparing equalization...` starts only after
  validation, preflight, and branch-name resolution, immediately before branch creation and merge.

## Test Plan

- Shared progress lifecycle test, including a rejected operation.
- Latest-owner progress tests for out-of-order completion and explicit invalidation.
- Ref-action tests for remote, workspace-changing, and deliberately excluded local mutations.
- Equalization timing tests proving preflight and modal messages remain outside its blocking
  mutation lifecycle, plus source-publication feedback coverage.
- Cherry-pick progress coverage and generated-webview timing contracts.
- Full `npm test`, `npm run quality:check`, `git diff --check`, and Graphify update.
