# Guided Bisect — Compact Controls

Date: 2026-10-11
Status: Approved and implemented; automated/Chromium verification passed; focused Extension Host smoke pending

The maintainer approved the proposed flow on 2026-10-11 with “Siga em frente.”

## Goal

Classify test revisions while keeping the graph available, without reopening the
full dialog for each answer. The maintainer requested Bug absent / Bug present
actions in the existing hidden-dialog banner, only after bisect starts, and a
clearer name for Hide. The supplied screenshot is the visual reference; retain
the existing bottom banner, theme tokens and graph viewport.

## Approved interaction

Rename **Hide** to **Minimize** and **Resume** to **Expand**. Minify suggests code
compression; Resume suggests the search is paused, whereas this presentation
change keeps the same session active. Both presentations control one search.

Example at normal panel widths:

```text
Step 8 · 23de35b    [Bug absent] [Bug present]    [Expand] [Stop…]
```

Keep the short current hash and step number visible, with the commit subject
available through accessible descriptive text. Give both answer buttons equal
visual weight; neither decision is the default. Cannot test, Undo, full history,
inspection and recovery remain available in the expanded dialog. Keep Stop's
existing confirmation and restoration behavior.

| State | Compact behavior |
| --- | --- |
| Preparing, before Start search | No answer controls; show Expand and Cancel. |
| Testing with a current commit, ready | Enable Bug absent / Bug present. |
| Local submission pending or host busy | Retain but disable answer controls; show Updating search… instead of implying the revision is ready. |
| Blocking error during testing | Disable answers, show a concise error and Expand for existing recovery controls. |
| Found, inconclusive, or bug predates interval | Remove answer controls; expand the result once when first reached, without an automatic checkout/restoration. |
| Session ended | Remove the banner and dialog as today. |

An already-started session is insufficient by itself: classification requires
the testing state and an actual current revision, with no pending operation or
blocking error. Each submission uses the existing repository/session/question
identity and existing host guards. The browser never performs a checkout.

After an ordinary answer and the next checkout, retain the minimized presentation,
announce the new hash and update the banner. Do not automatically focus either
answer button when a revision changes; use a neutral control if rebuilding the
banner removes the focused element. Keep keyboard navigation unrestricted so
the graph, editor and terminal remain usable.

In narrow panels, wrap context and controls into compact rows with full labels.
Keep horizontal/vertical graph scrollbars reachable. Use the existing theme and
visible focus styling for banner buttons as well as dialog buttons.

## Implementation assessment

The existing `renderBanner`, `control` and `request` helpers in
`src/revisionGraph/webview/runtime/bisectDialog.ts` can reuse the same actions,
pending state and validated protocol as the full dialog. Session updates already
retain the minimized presentation for ordinary answers (`reveal: false`). The
current renderer hides errors/results behind generic banner text, so those states
need explicit compact feedback and a one-time completion transition.

Scope is browser presentation, focused tests, styling and documentation. No Git
engine, contribution point, dependency or persistence changes are proposed.
The approved interaction is implemented within these boundaries.

## Acceptance and verification plan

- Before start and after completion, no compact classification is possible.
- Ready compact answers advance the same guarded session and keep it minimized.
- Duplicate clicks, busy state, errors and stale question versions cannot advance
  a revision; cleanliness remains enforced in the host.
- The displayed hash matches the question being answered, including answer/undo
  updates, reload recovery and repository changes.
- Completion becomes visible once; ordinary status updates never reopen it after
  the user minimizes the result again.
- Test focus after banner rebuilding, keyboard access, progress announcements,
  theme tokens and narrow panel wrapping in Chromium.
- Retain existing marker centering, manual scrolling and graph virtualization
  regressions; validate compact controls in an Extension Development Host.

## Implementation and verification

`bisectBanner.ts` owns compact labels, current-test eligibility, result-reveal
tracking and the banner DOM. `bisectDialog.ts` shares the existing action path,
announces local pending work, binds classification controls to the displayed
question and retains repository/version validation. Result reveal waits for busy
state to settle and resets when testing resumes after undo. When banner rebuilding
removes a focused control, focus moves to Expand with `preventScroll`; outside
focus is untouched. `bisectStyles.ts` provides grouped responsive controls, bounded
narrow-panel height, visible error feedback and theme-based focus/disabled states.
The new runtime source is included in `tsconfig.webview.json`.

Four added runtime regression tests failed before implementation and passed
afterward. They cover preparation and missing-current states, pending/duplicate
and detached stale answers, neutral focus, blocked recovery, all three result
statuses, one-time reveal, undo and session cleanup. The existing mock DOM's
`contains` now follows descendant ownership so focus behavior is tested accurately.

On 2026-10-11, `npm test` passed 1,024 tests including production and strict webview
builds, with no failures or skips. Quality passed for 293 production files / 2,783
functions; no quality threshold was raised. Chromium 122 / Electron 29.4.0 from
the VS Code 1.90 fixture passed 68 scenarios with the production runtime, real
session manager, graph-state builder and disposable Git checkouts. Coverage
includes compact progression, dirty-state recovery, undo, stale clicks, keyboard
navigation without a compact focus trap, commit-specific accessible button names,
equal decision styling, light/dark theme behavior and panel sizes from 220×300
through 1440×900. Previous marker movement/centering, completion and restoration
scenarios remained passing without native scroll listeners. No fixture JavaScript

Extension Host verification.
