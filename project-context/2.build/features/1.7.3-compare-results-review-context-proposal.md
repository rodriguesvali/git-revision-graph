# Preserve Compare Results Review Context — 1.7.3 Proposal

Status: Approved and implemented; final release smoke completed by maintainer confirmation
Date: 2026-10-03

## User Problem and Discovery

Keep the user's file filters and selection while the same comparison receives an
update. Currently an auxiliary update, such as generating an AI Compare Briefing,
clears the review context even when the compared references and files do not change.

Graphify queries surfaced the roadmap's Review Workflow Quality theme and
`CompareBriefingController`, `createCompareResultsWebviewState`, and the results
webview. An undirected extracted import path was:
`briefingController.ts -> aiBriefing.ts <- compareResultsWebview.ts`.
This path identifies shared contracts; the behavior was confirmed separately in
the source, not inferred from an import edge.

- `src/compareResultsView.ts:88`: briefing changes call `postState`.
- `src/compareResults/briefingController.ts:45`: generation enters loading, then
  ready/idle; cancellation also publishes a state change.
- `src/compareResultsWebview.ts:120`: every state message clears text search,
  resets the status filter to All, and resets selected IDs/selection anchor.
- `src/compareResultsView.ts:407`: existing worktree refresh after file restoration
  also publishes state. Automatic refresh on arbitrary file edits is not established.
- `src/compareResultsShared.ts:64`: item IDs combine path, status and revisions,
  without repository identity. Labels or file IDs alone cannot identify a session.

## Reproduced Evidence

Executed the actual message-listener code extracted from the generated Compare
Results HTML in a Node VM, with render/action callbacks stubbed. The comparison
and its two file IDs were unchanged; only briefing state changed from idle to loading:

| Review state | Before update | After update |
| --- | --- | --- |
| Text filter | `src/` | Empty |
| Status filter | `modified` | `all` |
| Selected IDs | `src/a.ts` | Empty |

This is a deterministic reproduction of the listener's reset, not a full browser
or live AI-provider test. No production code was changed during the proposal investigation.

## Proposed Scope and Acceptance Criteria

- Preserve text/status filters and valid selected IDs during updates within the
  same comparison session, including briefing progress/result/cancel and the
  existing worktree-refresh flow after restore.
- Explicitly identify the comparison session and repository at the host boundary;
  a new comparison resets the review context even if its displayed labels match.
  Switching repositories must never retain another repository's selection.
- Reconcile selection against the new authoritative items. Remove IDs that no
  longer exist; action dispatch must continue resolving current items and guards.
- Handle a status category disappearing or a filter returning zero files clearly,
  with available controls to return to the full list. Do not leave an invisible
  active filter or stale selection.
- Preserve the current single-file initial-selection behavior for a new comparison.

Exclude persistence across panel closure/VS Code reload, new search features,
sorting changes, new dependencies and Git-operation policy changes.

## Supporting Assessment and Risks

A focused Jev Choice preferred same-comparison preservation over briefing-only
handling, persistent review state across reopening, and deferring the change:
probability 0.85, confidence 0.82. This is supporting judgment, not verification
or maintainer approval. Its auxiliary rejection of the briefing-only alternative
against the reproduced reset was inconsistent with the supplied evidence and is
discarded; that alternative would fix the reproduced briefing case but not restore
refreshes. The primary evidence is the inspected and executed listener.

Expected scope: Compare Results host-to-webview identity, UI state reconciliation,
tests and documentation. No extra toolbar control is needed. Main risks are
confusing a refresh with a new comparison, leaking state across repositories, and
retaining invalid file IDs after restoration or status changes.

## Approved Implementation — 2026-10-03

The maintainer authorized implementation with "Pode seguir com a melhoria."
The approved scope is included in the 1.7.3 changelog and release plan.

- `src/compareResults/reviewSessions.ts` owns ephemeral identities in a WeakMap
  keyed by authoritative host state. IDs include repository path and a sequence;
  even a new comparison with identical labels receives a new identity.
- The host keeps an identity for briefing changes and explicitly transfers it
  across guarded worktree refreshes after restore or unified-diff preparation.
  Empty state has no identity. Request ownership and stale-operation guards are
  unchanged. Restoring a cached state after canceled loading recovers its original
  identity; request generations are deliberately not used as UI identity.
- `src/compareResults/viewState.ts` sends the optional identity to the webview.
  `src/compareResults/webviewReviewContext.ts` reconciles text/status filters,
  selected IDs and anchor against current items only within the same session.
  Missing or malformed identity, a new session, loading and empty state reset
  review context. Initial single-file selection is retained for new comparisons.
- The text input remains intact during same-comparison updates, preserving caret
  and typing focus. A focused file row is restored after rendering, or focus
  moves to the search input if that row disappears. Open menus close on updates
  so stale menu targets cannot survive a refresh.
- An active status filter stays visible with count zero; All and Clear remain
  available alongside the existing no-matches message. Selected items whose IDs
  disappear or change status are dropped, without selecting a replacement file.
- Existing nonce/CSP and inline Compare Results rendering are preserved. The
  revision-graph runtime, Git-operation policy, commands, dependencies, package
  version and persistence settings are unchanged.
