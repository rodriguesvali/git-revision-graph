# 1.7.5 — Bisect Answer Recovery

Status: Implemented; automated verification passed.
Approved: 2026-10-17, “pode tratar o item 2”.
Scope: B2 from the [bisect review](../bug-bisect-fragility-review-2026-10-17.md).

## Define

A native classification can succeed before the updated session log is durably
saved. Reload then sees a pending answer and the previous log and cannot resume
or restore, despite the native instance still belonging to this search. A second
window saves the new log but not the selection/cleared pending answer; the old
Retry repeats classification in that case.

Persist the exact pre-answer log with the pinned answer intent. Accept only that
single expected log extension on the same B1-verified native instance, save the
reconciliation before any subsequent mutation, and recover selection without
recording the answer twice. Preserve clean-worktree checks, message identity,
original destinations, owned undo and rejection of external replacements.

Acceptance: good/bad/skip recover after either storage window; found, inconclusive
and outside results remain correct; Stop/Undo work from the reconciled state;
unexpected commands/instances, invalid checkpoints and duplicate classifications
remain blocked. B3 target resolution remains separate.

## Build and external contract

`pendingAnswer.logBefore` is an internal bounded checkpoint, never sent to the
webview. `answerRecovery.ts` verifies an exact pinned classification extension.
The native fingerprint must match before any log discrepancy is reconciled.
Reconciliation is allowed only at control entry; command, checkout and reset
guards remain strict. A pending/rebuilding snapshot must be saved before running
the next operation even when an earlier failed write already updated memory.

Undo's rebuild uses its persisted ordered history as the intent ledger. Only the
next expected replay answer may extend its saved log; recovery then restarts the
owned rebuild deterministically. A newly started native instance whose identity
was not durably saved is still blocked by B1.

When already applied, native `git bisect next` recomputes selection using Git's
state without re-recording good/bad/skip or resetting/restarting the instance.
Only appended result comments are allowed for this selection command. The host
does not infer a culprit from comments or execute log/replay text. Starting and
classifying still use their existing exact command-log checks.

Context7 `/git/htmldocs` covered log/no-checkout behavior but did not answer the
specific `next` contract. The [official Git 2.55 source](https://github.com/git/git/blob/v2.55.0/builtin/bisect.c#L1289)
dispatches `next` to selection, separately from the function that writes a
classification. Disposable Git probes verified stable identity and no repeated
answer command. Runtime tests cover terminal states and retries.

Legacy pending answers without a checkpoint retain Stop/Undo recovery context;
Retry does not guess whether they were applied. A native start whose fingerprint
never reached storage remains unverifiable under B1 and requires manual recovery.
This change does not bypass that rule or introduce another persistence backend.
