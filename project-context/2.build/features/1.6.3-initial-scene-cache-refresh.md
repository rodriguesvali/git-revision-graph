# Initial Scene Cache Refresh Performance

Status: Implemented; automated and manual validation passed
Manual evidence: passed by maintainer confirmation on 2026-08-01; environment details were not supplied.
Target version: `1.6.3`

## Goal

Guarantee that the first ready revision-graph render collects rendered DOM element caches exactly
once, after the virtual scene markup is committed.

## User Workflow

1. The user opens or refreshes a large revision graph.
2. The ready-scene lifecycle prepares geometry, topology, and virtual indexes.
3. The first virtual commit mounts the visible node and edge markup.
4. Rendered node and edge element caches are collected once from that committed DOM.
5. Layout and highlights use the collected elements without a second scene-level scan.

## Scope

- Preserve the ready-scene lifecycle without a direct rendered-element cache refresh.
- Keep the virtual post-commit lifecycle as the single owner of the first ready DOM cache refresh.
- Retain the explicit refresh after clearing a non-ready scene.
- Add an integrated lifecycle regression that counts refreshes across the scene and virtual commit.

## Non-goals

- Changing graph topology, virtual indexes, markup, layout, search, selection, or minimap behavior.
- Moving projection or layout work to another process.
- Changing empty-state cache clearing.
- Adding a protocol message, setting, command, dependency, or contribution point.

## Acceptance Criteria

- The ready-scene lifecycle performs zero direct rendered-element cache refreshes.
- The first virtual scene commit performs exactly one rendered-element cache refresh.
- The combined first ready render performs exactly one refresh.
- A non-ready scene still refreshes caches after clearing its DOM.
- Cache collection remains ordered after markup commit and before layout/highlight synchronization.

## Risks And Controls

- A regression could reintroduce a second full DOM query in the scene lifecycle. The integrated
  test composes the typed scene and virtual lifecycles and asserts the individual and total counts.
- Removing all refreshes would leave layout and highlights with stale elements. The same regression
  requires the virtual commit to perform one refresh.
- Empty-state cleanup has a different ownership path. Its existing lifecycle assertion continues
  to require `clear -> dom-caches -> canvas`.

- Open and reload a large merge-heavy graph and confirm the first visible scene becomes interactive

- Open an empty repository state and confirm stale nodes and edges are cleared.

## Release-Note Impact

The first ready scene now has an explicit regression guaranteeing one rendered-element cache scan
instead of repeating the scan in both the scene lifecycle and virtual commit.
