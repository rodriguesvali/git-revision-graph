# 1.6.8 Nonblocking Remote Refresh

Status: Implemented; automated verification complete; manual smoke pending
Target version: `1.6.8`
Opened: 2026-08-22

## Goal

Keep the revision graph usable while Fetch, Pull, and Push contact a remote, without sacrificing
the refresh needed to show the resulting repository state.

## User Workflow

1. The user invokes `Fetch All Remotes`, `Pull from origin/...`, or `Push to origin/...`.
2. The graph displays subtle progress feedback without a pointer-blocking overlay.
3. Fetch and Pull rebuild history once; Push reapplies mutable refs over the loaded snapshot.
4. The final graph state replaces the progress feedback, or the previous state is restored on
   cancellation or failure.

## Scope

- Use subtle loading presentation for the remote operation and its graph refresh.
- Prepare Fetch refresh suppression before the Git mutation so expected repository events do not
  start a competing rebuild.
- Keep Fetch and Pull as full rebuilds because they may introduce or move local history and refs.
- Refresh Push as `projection-only`, preserving the snapshot cache and suppressing its expected
  repository state event; retain the controller's full-rebuild fallback when reuse is unavailable.
- Present Push progress consistently for normal and force modes.

## Non-goals

- No Git command, authentication, timeout, protocol, contribution point, setting, or dependency
  change.
- No change to Sync, Flow Governance remote probes, remote prompts, or mutation safety guards.
- No guarantee that a stale snapshot can always be reused after Push; safe fallback is retained.

## Acceptance Criteria

- Fetch and Pull show subtle progress during the remote operation and subsequent full rebuild.
- Fetch registers follow-up event suppression before invoking Git and cancels it on failure.
- Push shows subtle progress and schedules a projection-only refresh without clearing the snapshot.
- Push suppresses the expected repository state event and falls back safely when no reusable
  snapshot exists.
- Error, cancellation, repository ownership, and mutation-coordination behavior remain intact.

## Risks

- A remote operation may still take as long as the underlying network or Git provider requires;
  this change improves interactivity rather than changing Git timeouts.
- Snapshot reuse after Push depends on compatible graph options; fallback can still incur a full
  history load, presented subtly.

- Exercise a failed remote operation and a repository switch during an operation.

## Release-note Impact

Fetch, Pull, and Push now keep the revision graph interactive while showing subtle progress. Fetch
also avoids a redundant rebuild, and Push updates refs from the existing graph snapshot when safe.
