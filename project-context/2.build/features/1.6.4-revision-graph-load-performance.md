# Revision Graph Load Performance

Status: In progress; items 1-5 complete and verified
Target version: `1.6.4`
Baseline version: `1.6.3`

## Goal

Reduce the time from opening or refreshing the revision graph to the first interactive scene,
especially for large repositories, while preserving graph fidelity, cancellation, repository
isolation, and current webview behavior.

## User Workflow

1. The user opens or refreshes the revision graph in a repository with substantial history.
2. Git data, projection, layout, host-state construction, transport, and virtual rendering remain
   measurable and cancelable.
3. The first useful scene becomes interactive without waiting for avoidable auxiliary work or
   repeating unchanged graph-wide computation.
4. Repository status updates and projection-only refreshes preserve the current scene whenever its
   structural identity remains valid.

## Scope

- Establish an end-to-end baseline for cold load, warm load, projection-only refresh, host-to-webview
  delivery, and first interactive rendering.
- Evaluate parallel or deferred loading of merge, Flow Governance, and branch-description metadata.
- Remove Flow Governance Git metadata work that is unnecessary while governance is disabled.
- Evaluate reuse of the layout worker so cache misses do not repeatedly pay worker startup cost.
- Avoid full graph-state delivery and structural webview rebuilding for repository status-only updates.
- Remove verified duplicate projection, layout-result copying, and initial highlight synchronization
  from the measured critical path.
- Deliver the work in independently verified slices rather than one architecture rewrite.

## Non-goals

- Changing graph membership, projection semantics, layout output, focus behavior, or Git history limits.
- Weakening stale-result rejection, cancellation, multi-repository behavior, or webview validation.
- Adding a runtime dependency, command, setting, contribution point, persistent database, or provider API.
- Packaging a VSIX, publishing to Marketplace, or changing the `1.6.3` release artifacts retroactively.

### Item 2: Layout Worker Startup Amortization — Complete

- Replaced the one-projection worker protocol with explicit `calculate` requests and correlated
  result/error messages, each carrying a monotonically increasing request ID.
- Retain at most one healthy idle worker for sequential cache misses. Concurrent layout requests
  continue to receive separate workers, so the optimization does not introduce a global queue.
- Abort, timeout, message-deserialization failure, worker failure, unexpected exit, or synchronous
  `postMessage` failure terminates and discards only the affected worker. A calculated layout error
  leaves the worker reusable because the worker process remains healthy.
- Idle workers are unreferenced so they cannot keep the extension host or test process alive, then
  referenced again while active. Extension disposal terminates idle work and aborts active work.
- The locked `d3-dag` `1.2.1` worker shim requires a defined `workerData` object when its CommonJS
  bundle loads inside a Node worker; the persistent protocol therefore retains an empty bootstrap
  object and sends projections through `postMessage`.

### Item 5: Immutable Canonical Layout Cache Results — Complete

- Replaced the separate promise result, cloned persistence maps, and per-caller deep layout clones
  with one canonical cache result. Cache misses freeze the newly owned worker or fallback result
  once; concurrent callers and later hits reuse that same protected snapshot.
- Wrapped position and route maps in runtime read-only views that do not expose `set`, `delete`, or
  `clear`. Position objects, route objects, point arrays, and individual points are frozen before
  publication, so sharing cannot poison later cache hits even through untyped runtime access.
- Retained one defensive deep copy at the persisted-state restoration boundary. Mutable objects
  supplied by VS Code state are copied before freezing, so later changes to the input cannot alter
  the in-memory cache.
- Removed the redundant worker-result conversion clone and the extra persistence-only copies.
  Serialization now allocates only the required entry arrays over the immutable canonical values.
- Extended the deterministic CI benchmark with `layoutCacheHitMs` and exact cached position/route
  count assertions.

## Acceptance Criteria

- Trace output attributes the full load path from Git and host computation through delivery and the
  first interactive webview frame.
- Auxiliary metadata no longer serializes the critical path when it can be safely parallelized or
  delivered after the core graph.
- Disabled Flow Governance does not run branch-target or Pull Request readiness Git queries.
- Layout worker startup is amortized or is proven not to be a material cost on supported graph tiers.
- Status-only repository changes do not rebuild graph topology, virtual indexes, or scene DOM.
- Projection-only and full refreshes retain existing snapshot compatibility and metadata freshness rules.
- Deterministic tests preserve nodes, edges, layout, selection, search, minimap, and cancellation behavior.
- `npm run quality:check`, `npm test`, `npm run benchmark:ci`, and the applicable platform tests pass;
  RC benchmark and Extension Development Host evidence are recorded before release readiness.

## Risks And Controls

- Deferred metadata could arrive for a stale repository or render. Bind follow-up results to repository
  identity and render request IDs, and reject obsolete completions.
- Parallel Git work could increase process contention. Prefer eliminating or batching queries first,
  then use explicit bounded concurrency where parallel execution remains necessary.
- Reusing worker or cached data could leak state across repositories. Request IDs now bind every
  worker response to its active calculation; cancellation, bounded idle retention, cache identity,
  concurrency, recovery, and disposal are covered by focused tests.
- Partial host messages could desynchronize browser state. Extend shared protocol types, validation,
  authorization, handlers, and browser guards together for every delta message.
- Wall-clock benchmarks can be noisy. Keep deterministic functional assertions and record repeated
  cold/warm measurements without treating one local timing as a universal threshold.
